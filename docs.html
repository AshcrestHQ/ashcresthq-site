Contributing to AshcrestHQ

AshcrestHQ is built in the open — every line of Aegis and Janus exists because someone decided to contribute. Whether you're fixing a typo, squashing a bug, or building a whole feature, you're welcome here.

This guide covers how contributing works across all AshcrestHQ projects. Some repos may have additional notes in their own CONTRIBUTING.md — check there for project-specific setup.

Before You Start

  • Read our Code of Conduct — we expect respectful, constructive collaboration from everyone.
  • Join the Discord — it's the fastest way to ask questions, find collaborators, and hear about what's being worked on.
  • Not sure where to start? Look for issues tagged good first issue in any repo — these are scoped for newcomers.

Ways to Contribute

You don't need to write code to contribute meaningfully.

Type What it looks like
CodeBug fixes, new features, performance improvements
DocumentationImproving docs, fixing typos, writing guides or tutorials
DesignUI/UX feedback, icons, branding assets
Bug ReportsClear, reproducible issue reports
TestingTrying out new releases and reporting what breaks
TranslationLocalizing Aegis, Janus, or the website into other languages
CommunityHelping others in Discord, answering questions, welcoming new members

Reporting a Bug

Before opening an issue, search existing issues to avoid duplicates. When you do open one, include:

  1. What happened — a clear, specific description
  2. What you expected to happen
  3. Steps to reproduce — as minimal as possible
  4. Environment — OS, version, relevant config
  5. Logs or screenshots, if applicable

Found a security vulnerability? Do not open a public issue. See Reporting Security Issues below.

Suggesting a Feature

Open an issue with the enhancement label and describe:

  • The problem you're trying to solve (not just the solution)
  • Any alternatives you've considered
  • Whether you're willing to build it yourself

We'd rather discuss an idea before code is written than review a large PR that doesn't fit the project's direction.

Submitting a Pull Request

  1. Fork the repository and create a branch off main:
    git checkout -b fix/short-description
  2. Make your changes. Keep PRs focused — one fix or feature per PR is easier to review than five bundled together.
  3. Follow the existing code style in the file you're editing. If the project has a linter or formatter configured, run it before committing.
  4. Write clear commit messages — describe what changed and why, not just what file.
  5. Test your changes. If the project has a test suite, make sure it passes. Add tests for new functionality where it makes sense.
  6. Open the PR against main with:
    • A clear title
    • A description of what changed and why
    • A link to any related issue (Closes #123)
  7. Respond to review feedback. A maintainer will review your PR — expect some back-and-forth. This is normal and not a rejection.

Once approved and merged, you'll be recognized as a Contributor — including in our Discord, where the role is granted automatically.

Code Style

  • Match the formatting and conventions already used in the file you're editing.
  • Prefer clarity over cleverness. Code is read far more often than it's written.
  • Comment why, not what — the code already says what it does.
  • Keep functions and commits small and single-purpose.

Project-specific style guides (linters, formatters, naming conventions) live in each repo's CONTRIBUTING.md or docs/ folder.

Review Process

  • PRs are typically reviewed within a few days — larger projects or complex changes may take longer.
  • A Maintainer will review, request changes if needed, and merge once it's ready.
  • Don't take review comments personally — they're about the code, aimed at keeping the project solid for everyone who uses it.
  • If your PR goes quiet, a polite ping after a week is completely fine.

Reporting Security Issues

If you discover a security vulnerability in any AshcrestHQ project, do not open a public issue or discuss it in Discord.

Instead, email medhansh5@outlook.com or DM a Maintainer directly with:

  • A description of the vulnerability
  • Steps to reproduce
  • Potential impact

We'll respond as quickly as we can and credit you once it's resolved (unless you'd prefer to stay anonymous).

A Note on AI-Generated Contributions

AI tools are fine to use, but:

  • Disclose it in your PR description if a significant portion of the code was AI-generated.
  • Test and understand everything you submit — you're responsible for your PR, not the tool that helped write it.
  • Low-effort, unreviewed AI-generated PRs will be closed.

Recognition

Contributors aren't just names in a commit log:

  • The Contributor role in Discord is granted automatically once your first PR is merged.
  • Active contributors may be invited to join the Aegis Team or Janus Team, and eventually considered for Maintainer status.
  • All contributors are listed on our Team page.

Questions? Ask in #dev-help on Discord — we're glad to have you here.
